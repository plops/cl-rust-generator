## Vorschlaege fuer die Portierung

### 1. Rust vs. Kotlin: Keep Parts or Rewrite?

**Recommendation: Use a Hybrid Architecture (Rust Core + Kotlin UI).**

Here is why a 100% pure Kotlin reimplementation is problematic:

1. **AV1 Decoding is the primary bottleneck:**
   * There is **no mature, pure-Kotlin/Java AV1 software decoder**. 
   * On Android, while `MediaCodec` supports AV1 (API 29+), feeding it individual chunked still-picture OBUs per tile is notoriously brittle and adds buffer latency compared to `dav1d`/`rav1d`.
   * On Desktop JVM, you would need native C/Rust bindings (`dav1d` or FFmpeg) anyway.
2. **Protocol drift:**
   * The server and protocol types (`lbw-common`) are written in Rust. Sharing or binding the Rust types ensures you never have subtle serialization bugs, endianness mismatches, or YUV-to-RGBA conversion inaccuracies.
3. **Threading & Performance:**
   * Tile assembly, AV1 decoding, and pixel blitting onto a shared frame buffer run exceptionally well in native Rust without triggering JVM Garbage Collection pauses.

### 3. Step-by-Step Porting Guide

#### Step A: Generating the Rust ↔ Kotlin Bridge (UniFFI)
Instead of hand-writing raw JNI C bindings, use [**UniFFI**](https://mozilla.github.io/uniffi-rs/) (developed by Mozilla) or `android-ndk` with `uniffi`. UniFFI generates type-safe Kotlin bindings (`.kt`) directly from your Rust code.

Define an interface in Rust:

```rust
// In your rust wrapper crate (e.g. lbw_core)
pub struct LbwEngine {
    // holds Net, Scene, Decoder
}

pub trait LbwCallback: Send + Sync {
    fn on_frame_ready(&self);
    fn on_text_updated(&self);
    fn on_disconnected(&self, reason: String);
}

impl LbwEngine {
    pub fn new(host: String, port: u16, cb: Box<dyn LbwCallback>) -> Self { ... }
    pub fn send_key(&self, keysym: u32, mods: u8) { ... }
    pub fn send_char(&self, ch: u32) { ... }
    pub fn send_mouse(&self, x: u16, y: u16) { ... }
    pub fn send_button(&self, button: u8, down: bool) { ... }
    pub fn copy_rgba_to(&self, target_buffer: &mut [u8]) { ... }
}
```

#### Step B: Scene Rendering in Kotlin (Jetpack Compose / Compose Multiplatform)
In Compose, you can blit the frame buffer onto a `Bitmap` and draw the texts cleanly in the UI pass:

```kotlin
@Composable
fun RemoteDesktopScreen(engine: LbwEngine, sceneState: SceneState) {
    var bitmap by remember { mutableStateOf<ImageBitmap?>(null) }
    
    // Canvas drawing
    Canvas(
        modifier = Modifier
            .fillMaxSize()
            .pointerInput(Unit) {
                detectTapGestures(
                    onPress = { offset ->
                        engine.sendMouse(offset.x.toInt(), offset.y.toInt())
                        engine.sendButton(1, true)
                        tryAwaitRelease()
                        engine.sendButton(1, false)
                    }
                )
            }
    ) {
        // 1. Draw rasterized video canvas
        bitmap?.let { drawImage(it) }

        // 2. Overlay server text items on top with crisp rendering
        for (item in sceneState.texts.values) {
            drawRect(
                color = Color(item.bg[0], item.bg[1], item.bg[2]),
                topLeft = Offset(item.rect.x.toFloat(), item.rect.y.toFloat()),
                size = Size(item.rect.w.toFloat(), item.rect.h.toFloat())
            )
            // Draw text via DrawScope.drawText or standard TextLayout
        }
    }
}
```

### 4. Handling the SSH Tunnel in Kotlin

If you do not want the user to run an external terminal app (like Termux, ConnectBot, or OpenSSH), you can establish the SSH tunnel directly inside the Kotlin application before connecting `lbw-client`.

Using **Apache MINA SSHD** or **JSch**:

```kotlin
// Example using JSch for local port forwarding
import com.jcraft.jsch.JSch
import com.jcraft.jsch.Session

class SshTunnel(
    private val user: String,
    private val host: String,
    private val sshPort: Int = 22,
    private val remoteLbwPort: Int = 7878
) {
    private var session: Session? = null

    fun connect(privateKey: ByteArray?, password: String?): Int {
        val jsch = JSch()
        privateKey?.let { jsch.addIdentity("key", it, null, null) }
        
        session = jsch.getSession(user, host, sshPort).apply {
            password?.let { setPassword(it) }
            setConfig("StrictHostKeyChecking", "no")
            connect(10000)
            
            // Assign a local dynamic port (0 = pick any free port)
            // Forwards localhost:<assignedPort> -> server:remoteLbwPort
            val localAssignedPort = setPortForwardingL(0, "127.0.0.1", remoteLbwPort)
            return localAssignedPort
        }
        return -1
    }

    fun disconnect() {
        session?.disconnect()
    }
}
```

**Lifecycle Flow:**
1. App launches $\to$ user enters SSH credentials/key and server host.
2. Kotlin starts the SSH tunnel, binding remote port `7878` to local port `X`.
3. Kotlin starts the `LbwEngine` targeting `127.0.0.1:X`.
4. If the tunnel disconnects, Kotlin alerts the engine and attempts an exponential backoff reconnect.

## Bemerkungen zur Vorgehensweise

### 1. Review des bisherigen Plans: Ist er gut?

**Fazit vorweg:**  
Die architektonische Grundsatzentscheidung für ein **hybrides Modell (Rust-Core + Kotlin/Compose-UI)** ist **ausgezeichnet und die einzig pragmatische Lösung**. Sie verhindert, dass Sie einen komplexen AV1-Decoder in Java nachbauen müssen, garantiert bitgenaue Protokollkompatibilität zu `lbw-common` und hält den Speicherverbrauch gering.

Dennoch hat der Entwurf in der Praxis einige **kritische Schwachstellen, Fallstricke und Lücken**, die vorab behoben werden müssen:

---

#### Stärken des Plans
1. **Kein AV1-Neubau:** Die Wiederverwendung von `rav1d` spart Monate fehleranfälliger Arbeit und nutzt C/Rust-SIMD-Optimierungen auf ARM64.
2. **Keine Protokoll-Divergenz:** Reconnect-Logik, Sequenznummern, Tile-Assembler und Frame-Header bleiben in Rust identisch zum Desktop-Client.
3. **Klare Schnittstelle:** Trennung zwischen Netzwerk-/Dekodier-Engine und Benutzeroberfläche.

---

#### Kritische Schwachstellen & fehlende Aspekte

##### 1. Rust `cdylib` & JNI vs. UniFFI (Performance & Frame-Transfer)
* **Problem:** In Ihrem Entwurf fehlte in `rust-core/Cargo.toml` die Deklaration `crate-type = ["cdylib"]`. Ohne diese baut `cargo-ndk` nur ein Rust-Archiv (`.rlib`), aber **keine** dynamischen `.so`-Dateien in `jniLibs`.
* **Zero-Copy Frame-Puffer:** UniFFI serialisiert `Vec<u8>` über temporäre Puffer. Bei 640×640 RGBA (ca. 1,6 MB pro Frame) bei z. B. 30 Hz erzeugt das massive GC-Last auf Android.  
  * **Lösung:** Direkte JNI-Anbindung mit `java.nio.ByteBuffer.allocateDirect()` oder `AndroidBitmap_lockPixels`. Der Rust-Core schreibt direkt in den vom JVM-Grafiksystem gehaltenen Puffer.

##### 2. Fehlendes Mobile-UX- und Eingabekonzept
* Ein 640×640-Canvas ist auf modernen Smartphones (1080p bis 1440p) ohne Skalierung wenige Zentimeter groß.
* **Touch $\neq$ Maus:** Direkte Toucheingaben verdecken den Bildschirminhalt mit dem Finger. Auf einem Desktop-System benötigt man präzise Klicks, Rechtsklick und Hover.
  * **Lösung:** Zwei Modi anbieten:
    1. *Trackpad-Modus* (Standard): Der gesamte Bildschirm fungiert als Touchpad; Mauszeiger wird softwareseitig gerendert. Tap = Linksklick, Zwei-Finger-Tap = Rechtsklick, Zwei-Finger-Scroll = Rad.
    2. *Direkt-Touch-Modus* (für Touch-optimierte Oberflächen).
* **Sondertasten:** Android-Software-Keyboards haben kein `Ctrl`, `Alt`, `Esc`, `Tab` oder `F1..F12`. Es wird eine virtuelle Tastenleiste (Overlay) benötigt.

##### 3. SSH-Bibliothek: JSch (`mwiede/jsch`) vs. Apache MINA SSHD
* **Entscheidung:** Verwenden Sie **ausschließlich `com.github.mwiede:jsch`**.
* **Begründung:** Apache MINA SSHD zieht schwere Abhängigkeiten nach (Apache Commons, SLF4J, Java NIO2), was auf Android zu Dex-Konflikten und APK-Aufblähung führt. Der Fork von `mwiede/jsch` ist modernisiert (unterstützt `ed25519`, `rsa-sha2-256/512`), pure Java, extrem schlank und läuft out-of-the-box auf Android.

##### 4. Android Lifecycle & Standby (Doze Mode)
* Wenn das Smartphone gesperrt oder die App minimiert wird, kappt Android nach wenigen Sekunden den TCP-Socket.
* **Lösung:** Saubere Trennung bei `onStop()` / `onPause()` und optional ein schlanker *Foreground Service* mit Notification, falls der Tunnel im Hintergrund offen bleiben soll.

##### 5. GitHub Action Fallstrick (NDK-Pfad)
* `NDK_PATH=$(ls -d $ANDROID_SDK_ROOT/ndk/* | sort -V | tail -n 1)` kann fehlschlagen, wenn im Runner kein oder mehrere NDKs liegen. Besser ist es, in `androidApp/build.gradle.kts` eine feste `ndkVersion` (z. B. `"26.3.11579264"`) zu definieren und im CI-Workflow gezielt diese Version zu adressieren.

---

### 2. Fehlende Requirements: Konkrete Vorschläge

1. **Skalierung & Viewport:**
   * Pinch-to-Zoom und Panning (Verschieben des sichtbaren Ausschnitts bei Zoom > 1.0).
   * Scharfe Pixelskalierung (Nearest-Neighbor) beibehalten, damit Text in Unifont lesbar bleibt.
2. **Virtuelle Eingabeleiste:**
   * Einblendbare Leiste am oberen/unteren Rand mit: `Esc`, `Tab`, `Ctrl`, `Alt`, `F1` (HUD), `F2` (Auswahl), `F3` (Einfügen).
3. **Android-Berechtigungen:**
   * `android.permission.INTERNET` im `AndroidManifest.xml`.
4. **Verbindungsverwaltung:**
   * Profile speichern (Host, Port, SSH-User, SSH-Key/Passwort). EncryptedSharedPreferences verwenden.

### Fonts

Beim Desktop-Client liest `07_render.rs` die Schriftdatei hartkodiert aus dem Linux-Dateisystem (`/usr/share/fonts/.../unifont.otf`). Auf Android gibt es diesen Pfad nicht.

Hier ist die detaillierte Analyse, warum die Schriftart für dieses Protokoll kritisch ist und wie wir sie auf Android sauber handhaben:

---

#### 1. Warum GNU Unifont im Server-Protokoll unverzichtbar ist

Das Protokoll sendet Text als strukturierte Vektordaten (`ServerMsg::Text` mit `TextItem { id, rect, fg, bg, text }`).
* Der Server berechnet die Hintergrund-Boxen (`rect.w`, `rect.h`) basierend auf den Maßen von **GNU Unifont** (einem 8×16 bzw. 16×16 Pixel-Bitmap-Raster für fast den gesamten Unicode-Raum).
* Würde Android einfach die System-Schrift (*Roboto*) nehmen, ist diese **proportional** (ein `i` ist schmaler als ein `m`). 
* **Die Folge:** Der Text passt horizontal nicht in die berechneten Boxen, läuft über oder wird abgeschnitten, und Zeilen fluchten nicht mehr mit dem AV1-Canvas darunter.

---

#### 2. Die Lösung: Unifont als APK-Asset einbetten

Wir bündeln die TrueType/OpenType-Datei direkt im Android-Projekt unter:  
`android-app/app/src/main/assets/fonts/unifont.otf`

##### Dateigröße & APK-Overhead
* **Unkomprimiert:** ca. 12–14 MB (deckt die gesamte BMP / Unicode-Ebene 0 ab).
* **Im APK (Zip-komprimiert):** Die Datei schrumpft beim Packen des APKs auf nur **~3,5 bis 4 MB**.
* **Lizenz:** GNU Unifont steht unter der *GPLv2+ mit GNU Font Exception*. Durch die Font Exception wird der eigene Kotlin/Rust-Code **nicht** infiziert; die Schrift darf problemlos in der App gebündelt ausgeliefert werden.

---

#### 3. Exakte Nachbildung der Render-Logik (`07_render.rs`) in Kotlin

In `07_render.rs` gibt es zwei entscheidende Tricks:
1. Dynamische Schriftgröße abhängig von der Kachelhöhe (`11..=22 => 16 px`).
2. Horizontale Stauchung/Streckung (`font_scale_aspect`), damit der Text exakt in die Box gepresst wird.

In Jetpack Compose bilden wir das über `android.graphics.Paint` und `drawIntoCanvas` 1:1 nach:

```kotlin
// 05_ScreenRenderer.kt
package de.lbw.client

import android.content.Context
import android.graphics.Paint
import android.graphics.Typeface
import androidx.compose.ui.graphics.nativeCanvas
import androidx.compose.ui.graphics.drawscope.DrawScope
import androidx.compose.ui.graphics.drawscope.drawIntoCanvas

class TextRenderer(context: Context) {
    // 1. Unifont aus Assets laden, Fallback auf System-Monospace
    val typeface: Typeface = try {
        Typeface.createFromAsset(context.assets, "fonts/unifont.otf")
    } catch (e: Exception) {
        Typeface.MONOSPACE
    }

    private val paint = Paint().apply {
        typeface = this@TextRenderer.typeface
        isAntiAlias = false // Pixelschrift bleibt ohne Weichzeichner scharf
    }

    fun calculateFontSize(boxHeight: Int, zoom: Boolean): Float {
        val size = when (boxHeight) {
            in 11..22 -> 16f
            else -> (boxHeight * 0.8f).coerceIn(8f, 96f)
        }
        return if (zoom) size else (size * 9f / 16f).coerceIn(8f, 96f)
    }

    fun drawItem(
        drawScope: DrawScope,
        item: TextItem,
        scale: Float,
        zoom: Boolean
    ) {
        val r = item.rect
        val x = r.x * scale
        val y = r.y * scale
        val w = r.w * scale
        val h = r.h * scale

        // 1. Hintergrund-Box füllen
        drawScope.drawRect(
            color = androidx.compose.ui.graphics.Color(item.bg[0], item.bg[1], item.bg[2]),
            topLeft = androidx.compose.ui.geometry.Offset(x, y),
            size = androidx.compose.ui.geometry.Size(w, h)
        )

        // 2. Schriftgröße und Textbreite messen
        val fontSize = calculateFontSize(r.h, zoom) * (scale / if (zoom) 2f else 1f)
        paint.textSize = fontSize
        val measuredWidth = paint.measureText(item.text)
        if (measuredWidth <= 0f) return

        // 3. Aspect Ratio berechnen (exakt wie in 07_render.rs)
        val pad = scale
        val aspect = if (zoom) {
            1.0f
        } else {
            ((w - 2.0f * pad) / measuredWidth).coerceIn(0.4f, 2.5f)
        }
        paint.textScaleX = aspect
        paint.color = android.graphics.Color.rgb(item.fg[0], item.fg[1], item.fg[2])

        // 4. Baseline-Ausrichtung berechnen
        val fontMetrics = paint.fontMetrics
        val textHeight = fontMetrics.descent - fontMetrics.ascent
        val baseline = y + (h - textHeight) / 2f - fontMetrics.ascent

        drawScope.drawIntoCanvas { canvas ->
            canvas.nativeCanvas.drawText(item.text, x + pad, baseline, paint)
        }
    }
}
```

### 6. Konventionen für Commit-Messages (Conventional Commits)

Jeder Schritt muss mit einer präzisen, didaktischen Commit-Message nach folgendem Standard committet werden:

```text
<typ>(<scope>): <kurze beschreibung im präsens>

<ausführliche begründung: warum war die änderung nötig, was wurde gelöst>

- Detail 1
- Detail 2
```
* **Typen:** `feat` (neues Feature), `fix` (Bugfix), `refactor` (Code-Umbau ohne Verhaltensänderung), `test` (Tests hinzugefügt), `ci` (GitHub Action/Build-Anpassungen).
* **Beispiel:**
  ```text
  feat(rust-core): implement zero-copy direct bytebuffer rendering in 07_jni_bridge.rs

  Avoids intermediate memory allocation on JVM heap when passing 640x640 RGBA
  frames from Rust to Kotlin. Writes directly into ByteBuffer pointer.

  - Add direct buffer pointer lookup via JNIEnv
  - Implement bounds check against current scene dimensions
  - Add native unit test validating buffer stride alignment
  ```
